## 1. 0.2 线上实战踩坑实录（血泪经验，只有我们知道）

在 v0.2 从本地代码推向生产 VPS（`host173` / Caddy / Docker）的实测部署中，暴露出了一批极其典型但单测难以捕捉的生产级环境暗坑。本节将这些坑完整固化，防止后续迭代重蹈覆辙。

### 1.1 Fastify 5 实例级日志崩溃 (`FST_ERR_LOG_INVALID_LOGGER_CONFIG`)
- **踩坑现象**：本地所有单测全绿，但打成 Docker 镜像在生产环境启动时，主进程秒退，抛出错误：  
  `{"err": "logger options only accepts a configuration object.", "msg": "refusing to start"}`。
- **根本原因**：单测中为了静默输出，全部传入 `log: false`。而在生产环境的 `main.ts` 中传入的是由 `createLogger()` 生成的真实 Pino Logger 实例。  
  **Fastify 4 兼容直接传实例给 `logger`，但 Fastify 5 做了严格 Breaking Change**：
  - `logger` 参数**只允许传配置对象（Object）或布尔值（Boolean）**；
  - 若传入的是现成的 Logger 实例，**必须使用 `loggerInstance` 属性**，否则直接抛出 `FST_ERR_LOG_INVALID_LOGGER_CONFIG` 异常崩溃。
- **0.3 规范**：
  ```typescript
  const app = Fastify({
    ...(typeof options.log === "boolean"
      ? { logger: options.log }
      : options.log
        ? { loggerInstance: options.log }
        : { logger: false }),
    trustProxy: true,
  });
  ```

---

### 1.2 `trustProxy: false` 导致生产环境反向代理丢弃安全 Cookie
- **踩坑现象**：静态页面能打开，但调用 `/v1/csrf` 后，浏览器死活拿不到 `Set-Cookie: flytrap.sid`，紧接着调用 `/v1/login` 时服务端报错 `Missing csrf secret`，响应 `403 Forbidden`。
- **根本原因**：
  - 生产环境采用 `Caddy (HTTPS 443)` 反向代理到内部 `127.0.0.1:8080`（HTTP）；
  - Fastify 原代码硬编码了 `trustProxy: false`；
  - 在 `NODE_ENV=production` 下，会话 Cookie 强制启用了 `secure: true`；
  - 缺乏 `trustProxy` 支持时，Fastify 无法读取 Caddy 的 `X-Forwarded-Proto: https` 请求头，误以为当前请求是纯明文 HTTP，因此依据安全策略**悄悄将 `Set-Cookie` 字段丢弃**。由于没有持久化 Session，CSRF 校验所需的 `csrfSecret` 随之丢失。
- **0.3 规范**：
  - 只要服务跑在反向代理（Caddy / Nginx / Traefik）后方，Fastify 必须开启 `trustProxy: true`。

---

### 1.3 Google OpenAI 兼容端点 503 高峰排队与模型名称差异
- **踩坑现象**：配置 Google 的 OpenAI 兼容接口（`https://generativelanguage.googleapis.com/v1beta/openai/`）并使用 `gemini-flash-lite-latest` 时，偶发报 `openai 503`（Service Unavailable），短时间内连续触发重试直至任务被打死标为 `dead`。
- **根本原因与实测数据**：
  - `gemini-flash-lite-latest` 在 Google 官方 OpenAI 兼容层上容易遭遇官方集群排队高峰（503）；
  - 同一通道切换为 **`gemini-2.5-flash`** 后，实测响应时间从排队暴跌至 1~2 秒，且 100% 成功；
  - Google 的 OpenAI 兼容端点虽然兼容 `chat/completions`，但在流式缓冲、`response_format: { type: "json_object" }` 的兼容性上存在特定边缘行为。
- **0.3 规范**：
  - 引入原生 **Google GenAI SDK** 支持（非走封装层）；
  - 支持 **多 API Key 轮询与熔断（Multi-Key Pool & Fallback）**；
  - 支持 **跨模型降级链**（如：`gemini-2.5-flash` 遇 503/429 自动降级至备选 Key 或 `gemini-2.5-pro`）。

---

### 1.4 Docker Compose 的 `restart` 不重载 `.env` 配置文件
- **踩坑现象**：在服务器上修改了 `/srv/flytrap/.env` 中的 `OPENAI_MODEL`，执行了 `docker compose restart`，进入容器查看环境变却发现依然是旧模型。
- **根本原因**：`docker compose restart` 仅向运行中的容器发送重启信号（SIGTERM/SIGKILL），**不会重新读取宿主机的 `.env` 文件或重新生成容器配置**。
- **0.3 规范**：
  - 变更环境变量后，必须执行 `docker compose up -d` 触发容器的配置比对与重建（Recreate）。

---

### 1.5 任务打死（Dead Letter）缺乏前端一键复活与死信管理
- **踩坑现象**：当第三方模型接口偶发大面积 503 时，任务在指数退避达到 `max_attempts = 5` 后被标为 `dead`，邮件状态停留在 `error`。在此之后，即便修复了 API Key 或更换了模型，这些死信也只能通过手写 SQL 或重启进程触发 `--rebuild` 来救回。
- **0.3 规范**：
  - 在前端面板中提供 **死信队列（Dead Letter Queue, DLQ）管理**；
  - 支持在 UI 上一键“重新排队（Retry All Failed）”或单封重试。

---

### 1.6 宿主机物理数据绑定（Host Bind Mount）与权限
- **踩坑经验**：生产环境绝对禁止使用 Docker Named Volumes（匿名卷/命名卷），必须使用 Host Bind Mount（如 `/srv/flytrap/data:/srv/mail/data`）。
- **权限要点**：容器内非 root 用户 `node` 的 UID/GID 为 `1000:1000`。宿主机目录必须显式赋权：  
  `chown -R 1000:1000 /srv/flytrap/data`，否则 SQLite 创建 WAL 文件及 zstd 写入 EML 会报 `EACCES`。

## 3. 核心功能设计 (Features Spec)

### 3.1 彻底告别“屎绿色极简”，UI 体验现代化全面重构
v0.2 的前端采用零构建的原生纯 HTML，色彩搭配为极简军事风（军绿/墨绿），功能偏向极简列表查看。  
v0.3 将重构为一个现代、优雅、流畅的专业面板：

1. **视觉风格升级**：
   - 告别灰绿配色，引入现代科技感设计规范（Slate / Zinc / Indigo 色系，类 Linear / Vercel 质感）。
   - 完整的 **暗黑模式（Dark Mode）** 与明亮模式自由切换。
   - 优雅的排版、徽章（Badge）、威胁置信度环形进度与告警级别高亮（红/橙/黄/绿）。
2. **安全沙箱 HTML 邮件正文渲染**：
   - 当前只能查看清洗后的纯文本 (`text`)。
   - v0.3 增加 **HTML 安全预览器**：`iframe sandbox=""`（独立源，不授予脚本）加上页面 CSP。默认拦截外链图片与追踪像素，需要时再允许加载图片。
   - 支持 Tab 切换：【AI 分析摘要】/【格式化正文】/【原始 HTML】/【RFC822 原文 Header】。
3. **交互与操作流畅度**：
   - 邮件列表支持快捷搜索（发件人、收件人、主题、时间、威胁类型）。
   - 保留广受好评的“无刷新即时操作”，增加批量标记、批量重分类、快捷键（`j`/`k` 上下翻页，`r` 刷新）。

---

### 3.2 在线 AI 提示词与决策逻辑管理 (Online Prompt Editor)
目前提示词固化在磁盘文件 `prompts/classify-v1.txt` 中，微调策略必须 SSH 登录服务器修改。

1. **界面在线查看与热编辑**：
   - 在前端面板增加专门的 **【AI 策略与提示词 (Prompts)】** 选项卡。
   - 支持实时编辑系统提示词（System Prompt）模板与槽位规则。
   - 支持版本历史管理（例如 `v1.0`, `v1.1`, `v2.0`），提供“一键回滚”。
2. **在线单封调试 (Playground Mode)**：
   - 可以在网页端选择某一封已收到的邮件，选用草稿提示词进行“试跑测试（Dry Run）”，对比新旧提示词的分类输出差异，满意后再点击“发布并应用”。

---

### 3.3 原生 Gemini 支持 + 多 Key 智能轮换池 (Multi-Key Pool)
针对第三方 OpenAI 兼容层偶发 503、限速 429 的问题，彻底提升 AI 引擎的鲁棒性：

1. **原生 Google GenAI 驱动**：
   - 官方 `@google/genai` 原生接入，直连 Google 官方稳定链路，天然规避代理层缓冲。
2. **多 Key 轮换与健康度管理 (Key Pool Manager)**：
   - 配置格式支持逗号分隔多个 Key，或在面板动态维护：  
     `GEMINI_API_KEYS=key1,key2,key3`
   - **负载均衡**：Round-Robin 顺序轮换；
   - **错误熔断**：遇到 429（Quota Exceeded）或 503（High Demand）时，自动将该 Key 标记为冷却态（Cooldown 60s），无感切换到下一个可用 Key 重试；
   - 全体 Key 冷却时，退避等待并告警，不丢失任务。
3. **跨模型自动 Fallback 链**：
   - 优先级：首选速度极快的 `gemini-2.5-flash`；
   - 若遇到持续排队，降级尝试 `gemini-2.5-pro`。

---

### 3.4 精细化收件画像与自动化分流规则 (Rule Engine)
从单一的“接收并打标签”进化为可编排的邮件流控中心：

1. **邮箱地址画像（Mailbox Posture）维护**：
   - 前端支持维护不同收件地址的属性：
     - `canary`（探针蜜罐：任何发往此处的邮件默认极高可疑度）；
     - `active`（生产重要业务邮箱：精准分析鱼叉与社会工程威胁）；
     - `legacy`（历史废弃邮箱：碰撞监控）；
     - `wild`（任意盲扫前缀）。
2. **规则引擎（Rule Engine）**：
   - **白名单规则**：受信基础设施告警、认证完整的官方服务，直接标记 `legit` 并**短路跳过大模型调用**，节约 Token 并杜绝误判。
   - **黑名单规则**：明确已知的恶意发件 IP 网段、已知恶意发件域名，直接标记 `malware` / `phish`，免跑模型。

---

### 3.5 完善的死信队列与审计运维 (DLQ & Ops)
1. **死信队列可视化**：
   - 前端专属面板展示所有重试失败（`dead`）或处理报错（`error`）的任务；
   - 展示详细失败原因（如：`DNS timeout`、`OpenAI 503`、`JSON schema mismatch`）；
   - 一键批量重试（Re-enqueue）。
2. **一键索引重建与备份验证**：
   - 在面板提供管理员工具：触发全量扫描 `raw/` 目录重建 SQLite，实时反馈扫描进度与哈希一致性比对。

## 4. 技术栈选型与升级演进

| 模块 | v0.2 现状 | v0.3 演进 |
|---|---|---|
| **后端核心** | Node.js 22 + Fastify 5 + TypeScript | 保持（性能与类型安全极佳，生产验证稳定） |
| **API 鉴权** | Cookie Session + CSRF（`trustProxy: true`） | 保持 + 支持多管理员角色扩展 |
| **数据库** | Better-SQLite3（单文件，WAL，裸跑物理挂载） | 保持 + 补充规则表 `rules` 与提示词版本表 `prompts` |
| **AI 引擎** | 单一 OpenAI 兼容层 HTTP 调用 | **原生 Google GenAI + OpenAI 兼容双引擎 + Key Pool 轮换** |
| **邮件解析** | postal-mime（仅提取 text/urls/attachments） | postal-mime（增加安全 DOM 清洗的 HTML 结构体输出） |
| **前端实现** | 纯手写原生 HTML + 原生 JS（无打包工具，屎绿色） | **现代化组件面板（单文件轻量构建/Preact+Tailwind，深色模式，iframe 安全预览）** |
| **部署形态** | Docker Compose + Host Bind Mount（`/srv/flytrap/data`） | 保持物理 Bind Mount 规范，增加 Caddy 自动配置模版 |
