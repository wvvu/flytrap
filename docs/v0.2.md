# Flytrap — 垃圾邮件蜜罐 + AI 分类 · 架构规格 v0.2

> 给实现 agent 的可执行规格，不是随笔。
> 相对 v0.1 草案的硬约束：
> 1. **EML 是真源（别人的 SQL）**；SQLite 是派生索引（别人的 Redis）。永远可以从 EML 全量重建 SQLite。
> 2. **SQLite 表结构要稳**。会变的东西进 JSON 文本列，禁止为了 AI 输出加列。
> 3. **HTTP 先做标准 JSON API**，UI 只是其中一个消费者。仓库里不允许出现密钥、私钥、会话 secret、生产域名口令。
> 4. **协议层尽量用现成库，不手撸 SMTP / MIME / SPF-DKIM-DMARC。**

后续迭代另存 `ARCHITECTURE-v0.3.md`，不覆盖本文件。

---

## 0. 一句话系统

公网 MX 接到三个（可配置）域名的全部收件 → 一律 250 收下（本域 accept-all，绝不中继）→ 原始字节落盘并按内容哈希去重 → 异步做认证 / 解析 / 附件分桶 → AI 分类结果以版本化 JSON 写入 `ai_result` → 按规则推送摘要。管理面只走绑定在内网/本机的 JSON API。项目代号 **Flytrap**（捕蝇草）。

---

## 1. 非目标（写代码前先看）

- 不做发信、不做出站队列、不做 open relay。
- 不做 IMAP / JMAP / 用户邮箱。
- 不做前后端分离大前端（无 React/Vue 构建链）。允许一个极薄静态页或服务端模板消费 API。
- 不做 Redis / Postgres。v0.2 单机 SQLite + 进程内队列足够。
- 不在 SMTP 会话里跑 AI 或 DNS 重活（250 要快，认证/AI 全部异步）。
- 仓库不是配置源。域名列表、密钥、模型 key、推送 token 全部环境变量 + 挂载文件。

## 2. 技术选型（锁定理由，允许以后换实现不换边界）

### 2.1 必用

| 角色 | 包 | 版本意向 | 为什么用它，不选谁 |
|---|---|---|---|
| 运行时 | Node.js | 22 LTS 或 24 LTS | 与 `smtp-server` / `mailauth` 同一作者生态 |
| 语言模式 | ESM + TypeScript（strict） | TS 5.x | 给 agent 类型约束，少猜字段 |
| 收信 | `smtp-server` | 3.x（Nodemailer 配套） | **嵌入式库**，hooks 就是我们的流水线。Haraka 是完整 MTA + 插件框架，对本项目过重，且和「自己的归档/AI」抢控制权。WildDuck 是整套邮箱产品，直接否决。 |
| SPF/DKIM/DMARC/ARC | `mailauth` | 最新 | 一站式 `authenticate(buf, {ip,helo,sender})`，产出标准 Authentication-Results。不要自己拼 `spf`+`dkim`+`dmarc` 三套库。 |
| MIME 解析 | `postal-mime` | 最新 | mailparser 作者明确建议新项目用它；零依赖、有安全深度限制。附件流式需求弱（先落盘再解析），不需要 mailparser 的 Transform 流。 |
| SQLite 驱动 | `better-sqlite3` | 最新 | 同步、快、WAL 友好。收信路径要短，不要 `sqlite3` 的异步回调地狱。 |
| SQL 迁移 | 自研极薄 `migrations/*.sql` + 一张 `schema_migrations` | — | **不要 Prisma / Drizzle 当 schema 源。** 表要稳，JSON 列才是扩展点。ORM 会引诱人改表。查询用手写 SQL 或很薄的 repository。 |
| HTTP | `fastify` 5 | 最新 | 标准 JSON API、schema、日志、插件生态比 Express 更「API 正规」。UI 若用 htmx 也可以挂在同一进程不同 prefix，但 **契约以 JSON 为准**。 |
| 校验 | `zod` | 4 或当前稳定 | 环境变量、API body、AI JSON 都用同一套 schema。 |
| 日志 | `pino` | 最新 | fastify 默认；SMTP 进程共用。禁止 `console.log` 打正文。 |
| ID | `ulid` | — | 时间可排序，比自增更适合以后分库，比 UUID 好看。 |
| 哈希 | `node:crypto` `createHash('sha256')` | 标准库 | 对**压缩前原始字节**计算。 |
| 压缩 | `@mongodb-js/zstd` | 与 Node 20+ 匹配的主版本 | 预编译、API 就 `compress/decompress`。也可用系统 `zstd` CLI 做兜底，但代码路径锁定这一个库。**注意**：native addon，Windows 本地开发如果编译不过，可先用 `node:zlib`（gzip）跑通，容器里再切 zstd。代码抽一层 `compress/decompress` 接口即可换。 |
| HTTP 安全 | `@fastify/helmet` `@fastify/rate-limit` `@fastify/cookie` `@fastify/session` `@fastify/csrf-protection` | 配套 | 见 §8。 |
| 进程管理（容器内） | 一个 Node 进程先跑通；compose 里可拆 | — | 代码按「三个入口」组织，部署初期可以 `node src/main.ts` 全开。 |

### 2.2 明确不用（以及何时才考虑换）

| 不选 | 原因 | 何时再议 |
|---|---|---|
| Haraka | 配置/插件模型和本仓库抢控制权；accept-all + 自定义落盘用 hooks 更直接 | 单机日邮件 > 10 万且需要 rspamd 插件生态 |
| BullMQ / Redis | 多一个会扫端口的组件；本机量级用 SQLite job 表够 | 要水平扩 worker |
| Prisma | schema 变迁成本高，和「表要稳」相反 | 多实体复杂关系出现时 |
| JMAP / IMAP | 过度设计 | 永远不做，除非产品目标变了 |
| 把 EML 塞进 SQLite BLOB | 库会肥死，违背冷热分离 | 永不 |

### 2.3 AI / 推送：插件接口，不绑厂商

```ts
interface Classifier {
  id: string;                 // e.g. "openai-compat-v1"
  classify(input: ClassifyInput): Promise<AiResultV1>;
}

interface Notifier {
  id: string;                 // e.g. "telegram" | "ntfy" | "webhook"
  notify(input: NotifyInput): Promise<void>;
}
```

第一期实现一个 `openai-compat`（读 `OPENAI_BASE_URL` + `OPENAI_API_KEY` + `OPENAI_MODEL`），一个 `webhook` notifier。Telegram 作为第二个 notifier 实现，token 只来自环境变量。

### 3.2 三个运行角色

`main.ts` 读 `ROLES=smtp,worker,api`（逗号分隔）。

| 角色 | 监听 | 权限 | 做什么 |
|---|---|---|---|
| smtp | `SMTP_PORT`（生产 25） | 只写 raw + 插 messages/jobs | 尽快 250 |
| worker | 无端口 | 读 raw，写 attachments + 更新 JSON 列 | 认证/解析/AI/推送 |
| api | `API_HOST:API_PORT` 默认 `127.0.0.1:8080` | 只读 raw，写少量管理字段 | 面板与 JSON |

生产建议：**v0.2 三个角色必须跑在同一个 Node 进程**（`ROLES=smtp,worker,api`）。SQLite WAL 支持多进程读但写并发有限——smtp 插 messages/jobs 和 worker 更新 jobs/messages 会争用，`busy_timeout` 只能缓解不能消除。拆成多容器/多进程是 v0.3 的事，届时要么走写入代理，要么换 PostgreSQL。开发时三个角色同进程零问题。

### 3.3 Docker

- 非 root 用户跑 worker/api。smtp 若需 25：用 `cap_add: NET_BIND_SERVICE` 或宿主 iptables 把 25 DNAT 到 2525。
- 只挂载 `MAIL_DATA_DIR` 和只读配置（TLS 证书目录、提示词）。
- 镜像里不含 `.env`、不含证书私钥样例。
- `healthcheck` 打 `GET /healthz`（api）以及 smtp 的 TCP 探活。

## 4. SMTP 行为（必须按此实现）

### 4.1 服务器选项

```js
new SMTPServer({
  banner: process.env.SMTP_BANNER || 'mx',
  size: Number(process.env.SMTP_MAX_BYTES || 20 * 1024 * 1024),
  disabledCommands: ['AUTH'],     // 本机不提供投稿，避免被当成 relay
  authOptional: true,
  hideSTARTTLS: !tlsEnabled,      // 有证书再广告 STARTTLS
  disableReverseLookup: false,    // 要做 rDNS，结果进 session meta
  logger: pinoChild,
  onConnect, onMailFrom, onRcptTo, onData, onClose,
})
```

有证书时提供 `key`/`cert`（路径来自 env），开启 STARTTLS。没有证书也能收信（很多垃圾就是明文 25），不要因为证书缺失拒绝 DATA。

### 4.2 策略（policy.ts，纯函数，单测友好）

1. **绝不中继**：`onRcptTo` 里每个收件人的域名必须落在 `ACCEPT_DOMAINS`（逗号分隔，小写比较）。不是本域 → `550 5.1.1` 或 `550 5.7.1 relay denied`。这是防 open relay 的唯一闸门。`config.ts` 启动时必须校验 `ACCEPT_DOMAINS` 不为空、不含通配符、每个值是合法域名格式，否则拒绝启动。
2. **本域 accept-all**：本域任意 local-part 一律 250。不要查用户表。
3. **空 MAIL FROM（`<>`）允许**（bounce 形态的垃圾也要收）。
4. **连接级限速**：同 IP 并发连接数、每分钟连接数、每小时 DATA 数，超了 `421`。默认建议：并发 10 / IP，60 连接/分/IP，120 封/小时/IP，可用 env 调。
5. **体积**：超过 `SMTP_MAX_BYTES` 用 smtp-server 自带 SIZE，超了 552。
6. **VRFY**：smtp-server 默认不展开用户，保持即可。不要实现 EXPN。
7. **onData**：
   - 把 stream 收到 **内存上限 = SMTP_MAX_BYTES** 的 Buffer。**在 `stream.on('data')` 阶段实时累加字节长度**，一旦突破上限，立刻 `stream.destroy()`、解除引用，`callback(err)` 给 `552`。不能只在最后一步检查 size——那时内存已经爆了。
   - 立刻算 sha256。
   - 调 `storeRaw(buf)`：若哈希已存在，只追加一条「再次投递」记录或跳过落盘。
   - insert `messages` + enqueue `auth` job。
   - **`storeRaw` 真正完成 `fs.writeFile` 且哈希校验一致后，才能** `callback()` 给 250。落盘与应答必须具备确定性的先后一致。
   - 任何落盘失败（I/O 抖动、磁盘写满）：`callback(err)` 给 `451` 临时错，让对端重试。不要 250 了却没文件。

### 4.3 会话元数据（跟邮件一起进库，不进 EML 也要能重建认证）

`messages.smtp_meta` JSON：

```json
{
  "schema": 1,
  "remoteIp": "203.0.113.10",
  "reverseDns": "example.com",
  "helo": "mail.example.com",
  "mailFrom": "a@b.c",
  "rcptTo": ["x@yourdomain.com"],
  "secure": false,
  "receivedAt": "2026-09-21T08:00:00.000Z"
}
```

rDNS 查不到就 `null`，不要阻塞 250。

## 5. 存储：真源 vs 缓存

### 5.1 原则

| 层 | 存什么 | 丢了怎么办 |
|---|---|---|
| `raw/*.eml.zst` | 压缩前字节的精确副本 | 灾难。备份这一层。 |
| `attachments/*` | 附件原字节（不去 MIME 编码） | 可从 EML 再抽出 |
| SQLite | 指针 + 列表字段 + JSON 结论 | `worker --rebuild` 从 raw 全量重跑 |

**哈希规则（冻结）**

- SHA-256 对 **压缩前原始 EML 字节** 或 **解码后的附件字节**。
- 路径：`raw/{yyyy}/{mm}/{h0h1}/{h2h3}/{sha256}.eml.zst`
- 附件：`attachments/{h0h1}/{h2h3}/{sha256}`（无扩展名，MIME 进数据库）
- 换压缩算法只换后缀或 sidecar，不换哈希，不去重失效。

### 5.2 SQLite 模式（001_init.sql，之后尽量只加表不加列）

```sql
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;
PRAGMA synchronous = NORMAL;

CREATE TABLE schema_migrations (
  id TEXT PRIMARY KEY,
  applied_at INTEGER NOT NULL
);

CREATE TABLE messages (
  id            TEXT PRIMARY KEY,
  sha256        TEXT NOT NULL,
  raw_path      TEXT NOT NULL,
  size_bytes    INTEGER NOT NULL,
  received_at   INTEGER NOT NULL,
  envelope_from TEXT,
  envelope_to   TEXT NOT NULL,          -- JSON array
  message_id    TEXT,
  subject       TEXT,                   -- 列表用，可空
  from_addr     TEXT,
  to_addrs      TEXT,                   -- JSON，解析后
  domains       TEXT NOT NULL,          -- JSON array，收件域名
  smtp_meta     TEXT NOT NULL,          -- JSON，见 §4.3
  auth_result   TEXT,                   -- JSON，见 §6
  parsed        TEXT,                   -- JSON，见 §6
  ai_result     TEXT,                   -- JSON，见 §6  ★ 会变的结论都进这里
  status        TEXT NOT NULL,          -- received|authed|parsed|classified|notified|error
  error         TEXT,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);

CREATE UNIQUE INDEX idx_messages_sha256 ON messages(sha256);
CREATE INDEX idx_messages_received ON messages(received_at DESC);
CREATE INDEX idx_messages_status ON messages(status);
CREATE INDEX idx_messages_from ON messages(from_addr);
CREATE INDEX idx_messages_msgid ON messages(message_id);

CREATE TABLE deliveries (
  id            TEXT PRIMARY KEY,
  message_id    TEXT NOT NULL REFERENCES messages(id),
  received_at   INTEGER NOT NULL,
  smtp_meta     TEXT NOT NULL,
  UNIQUE(message_id, received_at, smtp_meta)
);
-- 同一封信（同 sha256）再次投递只加 deliveries，不复制 raw。
-- 实现时：若 sha256 已存在，messages 不插新行，只插 deliveries，并视策略决定是否重跑 AI。

CREATE TABLE attachments (
  sha256        TEXT PRIMARY KEY,
  path          TEXT NOT NULL,
  mime          TEXT,
  size_bytes    INTEGER NOT NULL,
  created_at    INTEGER NOT NULL
);

CREATE TABLE message_attachments (
  message_id    TEXT NOT NULL REFERENCES messages(id),
  sha256        TEXT NOT NULL REFERENCES attachments(sha256),
  filename      TEXT,
  content_id    TEXT,
  PRIMARY KEY (message_id, sha256, filename)
);

CREATE TABLE jobs (
  id            TEXT PRIMARY KEY,
  type          TEXT NOT NULL,          -- auth|parse|classify|notify|rebuild
  message_id    TEXT,
  payload       TEXT,                   -- JSON
  status        TEXT NOT NULL,          -- queued|running|done|failed|dead
  attempts      INTEGER NOT NULL DEFAULT 0,
  max_attempts  INTEGER NOT NULL DEFAULT 5,
  run_after     INTEGER NOT NULL,
  locked_at     INTEGER,
  locked_by     TEXT,
  last_error    TEXT,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);

CREATE INDEX idx_jobs_pick ON jobs(status, run_after);

CREATE TABLE mailbox_history (
  id            TEXT PRIMARY KEY,
  domain        TEXT NOT NULL,
  localpart     TEXT NOT NULL,
  first_seen    INTEGER,
  last_seen     INTEGER,
  source        TEXT,                   -- import|observed
  notes         TEXT,
  UNIQUE(domain, localpart)
);

CREATE TABLE audit_log (
  id            TEXT PRIMARY KEY,
  at            INTEGER NOT NULL,
  actor         TEXT NOT NULL,
  action        TEXT NOT NULL,
  target        TEXT,
  detail        TEXT                    -- JSON，不要写 secret
);
```

**禁止事项**

- 不要加 `ai_label` / `ai_score` / `is_phish` 这种会随模型变的列。列表筛选用 SQLite JSON1：`json_extract(ai_result, '$.label')`。若某筛选变热，**再**加生成列或索引，那是 v0.3 的事。
- 不要把正文、HTML、Authentication-Results 原文塞进独立列。它们属于 `parsed` / `auth_result` JSON，或直接读 EML。
- `parsed.text` 只存清洗后的截断纯文本（默认 20KB），全文以 EML 为准。

### 5.3 为什么 `ai_result TEXT` 是对的

AI schema 每个月都可能改字段。把结论做成：

```json
{
  "schema": 1,
  "prompt_id": "classify-v1",
  "model": "gpt-4.1-mini",
  "provider": "openai-compat",
  "at": "2026-09-21T08:01:00.000Z",
  "label": "phish",
  "confidence": 0.86,
  "summary": "仿冒网关重置密码，链接指向第三方域名",
  "tags": ["credential-theft", "lookalike-domain"],
  "signals": [
    { "name": "dmarc", "value": "fail" },
    { "name": "history", "value": "localpart never seen" }
  ],
  "raw": { }
}
```

- `schema` + `prompt_id` 让你可以并存多代结果，或在 `raw` 里塞厂商原始响应。
- 重跑分类 = 覆盖 `ai_result`（可选先把旧值 append 到 `ai_history` JSON 数组——若要做，用 `ai_result` 内部字段 `previous`，**不要新表**，除非真的要查询历史）。
- UI / notifier 只依赖 `schema === 1` 的那几个稳定键：`label|confidence|summary|tags`。

`auth_result` 同样版本化，直接存 mailauth 的精简投影 + 原始 headers 字符串：

```json
{
  "schema": 1,
  "spf": "fail",
  "dkim": "none",
  "dmarc": "fail",
  "arc": "none",
  "rdns": { "ptr": "example.com", "match": false },
  "headers": "Authentication-Results: ...\r\n"
}
```

`parsed`：

```json
{
  "schema": 1,
  "subject": "...",
  "from": { "name": "", "address": "" },
  "replyTo": null,
  "text": "截断纯文本",
  "htmlBytes": 1234,
  "urls": ["https://..."],
  "attachmentCount": 2
}
```

## 6. Worker 流水线

### 6.1 调度

- 单 worker 循环，**原子抢占**——严禁"先 SELECT 判断再 UPDATE"的非原子操作。使用单条语句完成锁定：

```sql
UPDATE jobs
SET status = 'running', locked_at = ?, locked_by = ?
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'queued' AND run_after <= ?
  ORDER BY created_at ASC
  LIMIT 1
)
RETURNING *;
```

- 崩溃恢复：启动时把 `running` 且 `locked_at` 过期的改回 `queued`。
- 失败：`attempts++`，指数退避写 `run_after`；超过 `max_attempts` → `dead`，message.status=`error`。
- 并发：v0.2 单 worker 串行即可。CPU/AI 才是瓶颈。不要一上来上线程池。
- **Graceful Shutdown**：收到 SIGTERM 时，worker 停止捞新 job，等当前 job 完成（或超时 30s 后标回 `queued`）再退出。SMTP 停止 accept 新连接，等当前 DATA 完成再关。

### 6.2 作业顺序

```
smtp 250
  └─ job auth
        └─ job parse          （auth 失败也继续 parse，蜜罐要看内容）
              └─ job classify
                    └─ job notify   （可按 label 过滤）
```

`auth`：`mailauth.authenticate(rawBuf, { ip, helo, sender: mailFrom, mta: SMTP_BANNER })`。**必须封装硬性超时熔断**（单个消息 DNS 解析总上限 10s）。垃圾邮件发送者的域名常配置恶意或瘫痪的权威 DNS。超时后作为"DNS 临时失败"记入 JSON，按指数退避重试，绝不允许外部 DNS 阻塞 worker 队列正常运转。DNS 重试上限 3 次。

`parse`：解压 raw → `PostalMime.parse` → 抽附件按内容哈希落盘 → 写 `parsed` + `message_attachments`。HTML 转文本用极简规则（去 script/style，剥标签，折叠空白），或 `html-to-text` 包。URL 用正则从 text+html 抽，最多 50 个。

`classify`：拼 prompt（见 §7）→ 调 Classifier → `AiResultV1.parse`（zod）失败则 job 失败。禁止把未校验的模型输出直接写入 DB。

`notify`：读 `NOTIFY_MIN_CONFIDENCE`、`NOTIFY_LABELS`（默认 `phish,malware`）。摘要里 **不要** 带完整正文，只带 subject / from / label / summary / 面板深链。

### 6.3 rebuild

`node src/main.ts --rebuild`：扫描 `raw/`，对 DB 缺失的哈希补 messages，对 `ai_result IS NULL` 的重入队。这是「SQLite 只是 Redis」这句话的验收标准。

## 7. AI 分类输入

系统提示词放 `prompts/classify-v1.txt`，用户消息由代码拼，结构固定：

```
AUTH: spf= fail dkim= none dmarc= fail rdns= no-match
ENVELOPE: from=<> to=admin@domain.tld
HEADER: From=... Subject=... Message-ID=...
HISTORY: localpart "admin" on domain.tld first_seen=2019 last_seen=2021 notes="旧主机面板"
TEXT:
...截断...
URLS:
- ...
ATTACHMENTS:
- invoice.pdf sha256=... mime=application/pdf size=220k
```

`mailbox_history` 三域历史在 classify 前按 `domain+localpart` 查，命中则注入 HISTORY 行。导入历史用一次性脚本读 CSV/JSON，走 `repos/mailbox-history.ts`，不要手改 DB。

模型必须只返回 JSON（prompt 里写死 schema）。代码用 zod 校验后写入 `ai_result`。

label 枚举冻结为：`legit | spam | phish | malware | gray | unsolicited-admin`。要加枚举只升 `schema` 版本，旧值仍能读。

## 8. HTTP API（标准、可扫仓库也不致命）

### 8.1 设计约束（对应「别哪天被扫到仓库看见洞」）

仓库允许公开的前提：

- 无默认口令。`API_PASSWORD` 未设置则 **拒绝启动 api 角色**。
- 无硬编码域名密钥、无 Telegram token、无 OpenAI key。
- raw 下载必须鉴权，路径穿越的防御必须是**物理级**的：取到路径后用 `path.resolve()` 还原规范化绝对路径，再用 `resolvedPath.startsWith(path.resolve(MAIL_DATA_DIR) + path.sep)` 严格前缀检查。**禁止**只靠检查是否包含 `..` 或把用户输入拼进 `fs.readFile`。即使数据库遭异常篡改，也无法突破数据目录的物理边界。
- 错误响应不回堆栈、不回本地路径。
- CORS 默认关。若以后要给独立前端，白名单来自 env。
- 会话：`HttpOnly` + `SameSite=Lax` + `Secure`（生产）+ 随机 `SESSION_SECRET`（≥32 字节）。
- 登录与写操作要 CSRF（cookie session 场景）。
- `API_HOST` 默认 `127.0.0.1`。文档写清楚：公网暴露必须反代 + TLS，且不要把 `/v1/messages/:id/raw` 放到 CDN。
- 登录接口每 IP 限速（例如 5 次 / 5 分钟）。
- 所有写操作记 `audit_log`（谁、何时、对哪封信做了什么）。

「和仓库解耦」的落地：

- 配置 = env + 数据卷，不读仓库里的 `config.json`。
- 提示词可以挂载覆盖 `/prompts`，镜像内只带默认 v1。
- CI 用 `.env.example` 做必填键检查，不用真实值。

### 8.2 认证

第一期：**单用户口令**（蜜罐面板不是多租户产品）。

- `POST /v1/login` `{ "username", "password" }` 比对 `API_USERNAME` / `API_PASSWORD`（用 `crypto.timingSafeEqual`）。
- 成功设 session。
- `POST /v1/logout`
- 除 `/healthz` `/v1/login` 外全部要 session。

以后要换 OIDC 只改 `api/auth.ts`。

### 8.3 路由（JSON，字段稳定）

基础：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/healthz` | `{ ok, roles, db: "ok" }` 不泄露版本和路径 |
| POST | `/v1/login` | 见上 |
| POST | `/v1/logout` | |
| GET | `/v1/me` | `{ user }` |

邮件：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/messages` | 分页。query: `label,status,q,from,domain,since,until,limit,cursor`。`q` 只搜 subject/from/message_id，不搜正文（正文在 EML）。 |
| GET | `/v1/messages/:id` | 元数据 + 解析 JSON + ai_result + auth_result，**不含**完整 EML |
| GET | `/v1/messages/:id/raw` | `Content-Type: message/rfc822`，从 zstd 解出。`Content-Disposition: attachment` |
| GET | `/v1/messages/:id/text` | 返回 `parsed.text` |
| POST | `/v1/messages/:id/reclassify` | 入队 classify |
| GET | `/v1/attachments/:sha256` | 鉴权后按哈希取附件，MIME 用库里的 |

管理：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/jobs` | 队列观测 |
| GET | `/v1/stats` | 今日/累计按 label 计数 |
| GET/POST | `/v1/mailbox-history` | 维护三域历史 |

列表项不要返回 `parsed.text` 全文、不要返回 `ai_result.raw`。详情才给。

分页用 cursor（`received_at + id`），不要 `OFFSET`。

### 8.4 UI

允许两种，二选一即可，agent 优先做 **最小静态页**：

- `GET /` 一套无构建的 HTML + 原生 fetch 调 `/v1/*`（带 cookie）。
- 或 fastify-view + htmx，但每个页面背后仍要有等价 JSON，禁止「只有 HTML 片段、API 以后再说」。

UI 不是安全边界。安全边界在 API。

## 14. 扩展与演进建议（RFC / Backlog）

> 本节整理针对多域名拓扑、收件人画像、规则分流及告警降噪的实现建议,随需求逐步下发实现。

### 14.1 多域名与多网卡接入 (Multi-Domain & Multi-IP)
- **多域名解析**：保持单个服务实例，外部各域 MX 统一指向本机。`ACCEPT_DOMAINS` 继续沿用环境变量逗号分隔，在应用层转为 `Set<string>` 进行 $O(1)$ 匹配，未命中严格阻断 `550 Relay denied`。
- **多 IP 溯源**：若宿主机绑定多公网 IP，SMTP 监听 `0.0.0.0`。建议在 `messages.smtp_meta` JSON 中追加 `localIp` 与 `localPort` 字段。仅记录物理网络特征，不为了多 IP 增加额外的网络分流抽象。

### 14.2 邮箱状态画像与维护 (Mailbox Posture)
- **收件人语义分级**：外部一律响应 250，内部按威胁暴露面赋予收件地址不同属性：
  - `active`：真实在用邮箱，若遭遇鱼叉攻击则威胁等级最高。
  - `canary`：主动撒播在公网的诱饵地址，命中即确认来自爬虫或黑产遍历。
  - `legacy`：已废弃的历史邮箱，常用于捕获陈旧凭据泄漏碰撞。
  - `wild`：字典盲扫与未知前缀，按通用基线处理。
- **配置与维护**：复用现有的 `mailbox_history` 表结构，通过补充 `type` 字段（默认 `wild`）实现。
- **接口扩展**：API 暴露 `POST /v1/mailbox-history`（支持单条）与 `POST /v1/mailbox-history/batch`（支持批量 JSON/CSV 导入），前端提供极简表格与上传按钮。
- **流水线注入**：在 `job-classify` 阶段检索目标地址画像，作为确定性事实注入提示词的 `HISTORY:` 槽位。

### 14.3 黑白名单规则
- **真源不可侵犯**：**绝对禁止在原始 EML 中写入任何自定义 X 头**。向原始字节流注入标记会破坏 SHA-256 基准、导致原邮件 DKIM/ARC 校验偏转，并彻底破坏从 raw 重建数据库（Rebuild）的能力。
- **短路规则引擎建议**：黑白名单应作为 `job-classify` 之前运行的静态规则引擎，存储于代码配置或独立的轻量 `rules` 表：
  - **命中白名单**（如已知基础设施告警、受信合作伙伴）：直接生成派生的 `ai_result`，标记 `legit` 与命中规则，**短路跳过大模型调用**，节约 API 成本并杜绝误报。
  - **命中黑名单**（已知恶意网段、特定滥用发件特征）：直接判定为 `spam` 或 `malware`，同样免跑模型。
  - 所有判定轨迹均记录在 `ai_result.signals`，保证原始文件与派生状态职责清晰。

### 14.4 威胁分级与通知降噪 (Priority & Throttling)
- **分级必要性**：公网开放 MX 会伴随持续的机械扫描与垃圾碎片，缺少分级的即时推送会导致通道被刷屏，引发严重的警报疲劳。
- **推荐策略（四级制）**：在 `job-classify` 完成后，由代码根据模型结论与收件人画像计算 `priority`：
  - `critical` (P0)：命中 `active` 邮箱的高置信度钓鱼/高危附件攻击。**立即推送全渠道**。
  - `high` (P1)：针对未废弃域名的高置信度恶意载荷。**立即推送**。
  - `medium` (P2)：常规撞库推广、灰色营销。**不触发即时推送**，归入每日汇总报表。
  - `low` (P3)：退信探测、格式损坏邮件、白名单豁免邮件。静默归档。
- **流控参数**：可在环境变量中引入 `NOTIFY_MIN_PRIORITY=high`，由用户按需控制通道信噪比。
